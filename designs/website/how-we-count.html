The method

Same tool, same model, same tasks.

The only difference between the two arms of a test is whether Artifice is connected. Every comparison is paired: the same task, run in both arms.

The same AI tool

Claude Code 2.1.308, the same pinned copy in every run, run without a person at the keyboard. No user settings, memory, skills or plugins.

The same model

Claude Sonnet 5.5 at effort high in both arms. The model that graded answers, Claude Opus 5.5, never wrote them.

The same tasks

Each question or issue runs in both arms, given exactly as typed. Tasks used to tune Artifice are kept apart from the ones it is scored on.

Without Artifice

Claude Code on its own

  • Finds what it needs with its own search and read tools.
  • Works on the benchmark's own copy of each project, never the original.
With Artifice

Claude Code, connected as artifice connect does it

  • The MCP server and the hooks, exactly as a person gets them.
  • Its own Artifice data, kept apart from anything we use day to day.
The three benchmarks

What we asked, and what we found.

1 · Questions about code

How does this codebase work?

Date

Version
Artifice 0.1.7
Projects
5: two of ours, three open source
Questions
144 held out, 1 run per arm
Judged by
Claude Opus 5.5, 0–10, blind

Five projects: a Unity game of about 10,000 files and a planning folder, both ours, and three open-source projects at fixed commits: memos (Go and TypeScript), httpie (Python) and pocketbase (Go and JavaScript). Artifice was never tuned on pocketbase.

Claude Opus 5.5 explored each project read-only and wrote questions the way people type them, each with the files that answer it. A second Opus session checked every one with tools; 278 of 287 survived. Half were used to tune Artifice, and the rest were scored once. Claude Code ran read-only.

With Artifice, Claude Code spent 27.8% less per question and took 4.2 turns instead of 6.4. It was cheaper on every project, by 20% to 37%. Scores didn't move: the paired difference was +0.01, with a 95% confidence interval of −0.17 to +0.22. The version before, 0.1.6, saved 12.2% on the same questions.

The folder holds 45 files: 16 documents we generated from known text, one per format, six real public PDFs such as a 492-page security standard and a company's annual report, and 24 real Office and Outlook files from Apache Tika's public test set.

Opus 5.5 explored the folder and wrote 68 questions, each checked by a second Opus session. Ten were general questions that get no briefing in either arm, which leaves 58. Shell commands were allowed in both arms, so Claude Code could open Office files itself without Artifice.

With Artifice, answers scored 8.16 out of 10 against 6.62, at 12.7% lower cost and in 3.6 turns instead of 5.5. The version before, 0.1.7, skipped these files and made the same folder 51% more expensive.

3 · Fixing code

Fix this GitHub issue.

Dates
October 22 and 26, 2026
Version
Artifice 0.1.6
Tasks
50 issues from 43 repositories
Runs
3 per task, 150 per arm
Judged by
The benchmark's own tests

The tasks are real GitHub issues from SWE-rebench's March 2026 set, created after the model's training, drawn at random with a fixed seed. We first tried the well-known SWE-bench Verified Mini, but the model named the file to change for 94% of its tasks from the issue text alone, so it measured memory, not search.

Each run started from a fresh copy of the repository with no history, so the real fix couldn't be found. Claude Code had no shell and no web access. Every patch was scored by the benchmark's official test harness, in Docker.

With Artifice, a task cost the same: −0.1%, with a 95% confidence interval of −3.5% to +3.2%. Earlier versions cost 9% to 11% more. Even when we handed Claude the exact lines the real fix changes, it cost the same, because it finds the place in a few steps on its own. So Artifice now tells a question from a change on your computer, and adds nothing to a change.

Judging

How we decided an answer was right.

Questions: graded against a checked answer

Every question came with a reference answer, checked by a second Opus session with tools. Claude Opus 5.5 graded each answer from 0 to 10 against it, without being told which arm wrote it.

Fixes: the benchmark's own tests

A patch counts as solved only if the benchmark's tests pass. Before any run, each task's real fix was scored on our machine; four that couldn't be scored there were replaced by the next tasks in the fixed random order, as decided in advance.

Statistics: paired, with confidence intervals

Each task is compared with itself in the other arm, and every difference comes with a 95% confidence interval. When an interval includes zero, we call it no difference.

Tokens saved in the app

What “about 128k tokens saved” means.

The app can't rerun your question without Artifice. So each question Artifice answers counts what an answered question saved when we measured it, priced at your AI's prices.

The figure per question comes from a public benchmark of questions developers asked about 15 popular Python projects (SWE-QA-Bench): 60 held-out questions, each asked twice in each arm, in Claude Code with Sonnet 5.5 and Artifice 0.1.6. With Artifice, each question cost 3.8% less, with the same answer quality.

It is the smallest saving we have measured on questions: the later benchmarks above saved more. When your AI is on a subscription, money is shown as what the same use would cost at API prices.

What counts nothing. Requests to change code, which get no briefing. Previews in Library and Playbooks. Questions from other AI tools count the figure measured in Claude Code, and the app says so for each of them.

Limits

What these numbers don't show.

  • One AI tool and one model.Every run used Claude Code with Claude Sonnet 5.5. Cursor, Codex and the other tools work differently, and we haven't measured them yet.
  • AI-written questions and an AI judge.Claude models wrote and checked the questions and graded the answers. Differences under a point are within the judge's noise.
  • One run per question.The code and document question benchmarks ran each question once per arm. The fix benchmark ran each task three times.
  • One folder of documents.Partly generated, partly public test files. Your company's documents will differ.
  • Single, self-contained tasks.Long sessions and repeated work on the same project weren't measured.
  • Projects the model may know.Popular open-source projects are partly familiar to the model, which tends to shrink a measured saving.
  • English first.Search by meaning uses an English model, so questions and documents in other languages are matched less well.
  • Scans and images on a Mac only.Text recognition uses the Mac's own; on Windows, scans and pictures aren't read yet.
